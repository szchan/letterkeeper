# LetterKeeper 需求文档

版本：0.1 · 日期：2026-10-12 · 状态：需求基线，尚未实现。

## 1. 项目定位与已确认决定

LetterKeeper 是隐私优先、轻量、同时服务于人和 Agent 的开源邮件客户端。项目目录为 `~/Projects/letterkeeper`，仓库和命令名称使用 `letterkeeper`。

用户已确认使用 GNU GPL 第 3 版；当前项目许可标识为 `GPL-3.0-only`，见 [LICENSE](../LICENSE)。项目概要见 [README](../README.md)，后续开发遵循 [AGENTS.md](../AGENTS.md)。

首要平台为 Linux；本机为 Omarchy/Arch x86_64。TUI 是优先交互方式，界面应精致、清晰并支持中文。GUI、其他平台与移动端作为后续选项，当前不选定实现框架。

需求优先级：P0 为首个可用于真实邮箱的版本必须满足；P1 为后续改善；待定项需要在实现前记录选择及理由。

## 2. 用户场景

1. 用户通过 Gmail OAuth 登录，在终端查看、搜索、回复和发送邮件。
2. 用户阅读 HTML 邮件的安全文本表示，发件者的资源服务器不会因此收到请求。
3. Agent 通过本地 MCP 查找和总结指定邮件、准备回复、保存草稿；按用户授权发送。
4. 用户和 Agent 共用账户与邮件状态，但可以给 Agent 设置更窄的访问范围和操作权限。
5. 用户查看诊断和性能信息时，不会意外泄露邮件正文、邮箱地址或 OAuth 凭据。

## 3. 威胁模型与范围

需要防护的输入包括恶意 MIME、HTML/CSS/SVG、脚本、带唯一标识的资源 URL、畸形附件、控制字符，以及邮件中诱导 Agent 执行操作的文本。

保护重点：阻止默认阅读和解析带来的远程追踪、正文脚本执行、无授权发送、凭据泄露、路径访问和资源耗尽。不能仅以“过滤追踪像素”“移除图片 URL”或“DOM 不执行脚本”证明已实现保护。

邮箱服务商仍可记录合法连接、IP 和 IMAP 状态；云端模型仍会收到 Agent 所读取的内容。用户主动打开链接、执行附件或放行资源会引入额外风险。项目目标不是匿名邮箱服务或默认端到端加密，也不保证发件者无法通过用户主动回复等行为推断阅读。

## 4. 邮件功能

| 编号 | 优先级 | 要求 |
| --- | --- | --- |
| MAIL-01 | P0 | 支持 IMAP 与 SMTP，强制安全连接并验证证书；不静默降级到明文或跳过证书验证。 |
| MAIL-02 | P0 | 支持邮箱文件夹、列表、分页、正文、搜索、回复、全部回复、转发、草稿、发送和常用标记。 |
| MAIL-03 | P0 | 正确处理 MIME、multipart/alternative、常见字符集、中文、邮件线程与回复头。 |
| MAIL-04 | P0 | 附件可列出、保存和添加；不自动执行、预览或打开，限制路径、文件名和输入大小。 |
| MAIL-05 | P0 | Drafts/Sent 行为明确；验证草稿和已发送邮件的服务器同步，不制造重复已发送副本。 |
| MAIL-06 | P0 | 提供不修改已读状态的读取；Agent 读取默认使用该模式。用户 TUI 的自动标记已读策略可配置。 |
| MAIL-07 | P0 | 发送超时、断连时区分失败与结果不确定，不盲目重试，提供避免重复发送的恢复流程。 |
| MAIL-08 | P1 | 多账户统一管理、离线缓存与本地搜索；首次版本至少确保接口不阻碍后续多账户支持。 |
| MAIL-09 | P1 | 删除、移动、归档等操作提供明确语义与可恢复流程；Gmail 标签和归档语义单独验证。 |

## 5. 登录与数据保护

| 编号 | 优先级 | 要求 |
| --- | --- | --- |
| AUTH-01 | P0 | 支持 Gmail OAuth 浏览器授权、续期、注销和撤销后的可理解错误；不要求将应用专用密码冒充 OAuth。 |
| AUTH-02 | P0 | 支持标准 OAuth/XOAUTH2 等协议认证接口；通用 IMAP/SMTP 也可使用安全保存的账户凭据。 |
| AUTH-03 | P0 | 优先使用系统凭据存储；refresh token、密码与 client secret 不写进普通配置、命令参数、工具响应或日志。凭据存储不可用时不静默降级为明文。 |
| AUTH-04 | P0 | 邮件直接连接服务商，不要求经开发者的中转服务器；不借用其他客户端的 OAuth 身份。 |
| DATA-01 | P0 | 本地私有文件有合理权限，缓存位置和清理行为明确；日志默认不保存敏感内容。 |
| DATA-02 | P0 | 不内置默认遥测或上传邮件的崩溃报告；错误诊断可供用户主动导出，并去除敏感信息。 |
| DATA-03 | P1 | 在威胁模型和性能评估后确定邮件缓存的静态加密方案；首次版本不声称已有加密保护。 |

Gmail OAuth client 的注册、个人自用与公开发布流程尚待设计。个人使用验证豁免与公开分发要求分别核实，不能承诺使用者永远无需注册自己的 OAuth client。

## 6. 正文隐私与安全

**核心验收条件：默认阅读、解析、转换和 Agent 展示邮件，均不因正文内容发出外部请求，也不执行正文脚本。** 正常 IMAP/SMTP/OAuth 联网不属于被禁止的正文请求。

| 编号 | 优先级 | 要求 |
| --- | --- | --- |
| PRIV-01 | P0 | 禁止正文自动加载所有远程资源，包括图片/srcset、CSS/@import/url()、字体、媒体及封面、iframe/object/embed、SVG 外部引用和预取。检查 HTTP 与 DNS 行为。 |
| PRIV-02 | P0 | 禁止内联及外部 JS、事件处理属性、javascript: URL、脚本式 SVG 和其他正文主动执行入口。 |
| PRIV-03 | P0 | 保护必须在解析前生效。首选无资源获取能力的解析器；浏览器引擎方案必须独立控制网络，隔离失败时拒绝处理。 |
| PRIV-04 | P0 | HTML 输出采用安全文本/白名单结构；不把原始 HTML 直接交给 GUI、终端或 Agent 渲染。不用正则作为唯一 HTML 消毒机制。 |
| PRIV-05 | P0 | 本地 MIME 内嵌资源与远程 URL 明确区分。CID 图片只有经受限解码和安全显示路径才可展示，不允许嵌套资源或脚本借此联网。 |
| PRIV-06 | P0 | 不自动发送 MDN 已读回执；IMAP 已读状态与发给发件者的回执分别处理。 |
| PRIV-07 | P0 | 不自动访问链接、提交表单、执行导航/刷新、加载链接预览或打开附件；用户主动操作应显示真实目标和权限影响。 |
| PRIV-08 | P0 | 处理危险终端控制序列、双向文本欺骗、畸形/超大 MIME、压缩内容和超长正文；设置解析与显示的资源边界。 |
| PRIV-09 | P1 | 若提供手动加载资源，仅针对明确的单封邮件/资源授权；不得为完整 HTML 显示自动放开脚本，也不得隐式形成永久发件者白名单。 |

仅返回 Markdown 不满足 PRIV-04：Markdown 图片、原始 HTML、链接预览及自动导航也需要防护。仅选择 text 输出也不能证明上游 HTML 转换过程无外联。

## 7. Agent 与 MCP

| 编号 | 优先级 | 要求 |
| --- | --- | --- |
| MCP-01 | P0 | 提供本地 MCP stdio 接口，兼容 Codex 等标准 MCP 客户端；协议输出与诊断日志分离。 |
| MCP-02 | P0 | 提供账户/文件夹列表、搜索、读取、创建/保存草稿、回复草稿和发送；复用核心后端，不维护两套独立邮件逻辑。 |
| MCP-03 | P0 | 默认仅按需返回有限正文和元数据，支持分页和截断提示；完整正文与附件获取为显式操作，不把整个邮箱自动塞入模型上下文。 |
| MCP-04 | P0 | 账户、文件夹和操作范围可配置；支持只读、可起草、可发送权限。策略由用户配置，邮件或模型不能自我提权。 |
| MCP-05 | P0 | 默认允许起草和审阅，发送需实际用户授权；支持用户预先配置受限自动发送。模型填写 confirm=true 不能充当权限边界。 |
| MCP-06 | P0 | 授权与实际发送内容绑定，覆盖账户、收件人、主题、正文、附件；内容变更需重新满足授权条件。 |
| MCP-07 | P0 | 邮件内容明确作为不可信数据；不因正文指令自动打开 URL、调用其他工具、读取文件、上传数据或发送邮件。 |
| MCP-08 | P0 | 邮件解析和输出都满足 PRIV-01 至 PRIV-08；消费者把文本作为文本显示，并禁用远程资源、原始 HTML 和预览。不支持安全展示时采用保守格式或拒绝该路径。 |
| MCP-09 | P0 | 凭据不暴露给 Agent；发送结果明确报告已发送、失败或不确定，并提供关联标识。 |
| MCP-10 | P1 | 本地 HTTP MCP 可作为后续选项，需认证和访问控制；首个版本不暴露公网服务。 |

本地 MCP 不保证模型本地处理。文档应明确哪些内容会交给用户所选模型；未来可支持本地模型，但首版不绑定某个 LLM 或云端 SDK。

## 8. 界面与性能

| 编号 | 优先级 | 要求 |
| --- | --- | --- |
| UX-01 | P0 | TUI 优先；布局精致、信息层级清晰，支持中文/宽字符、键盘导航、帮助和可理解的错误。 |
| UX-02 | P0 | UI 不因邮件网络请求或正文解析长时间阻塞；支持取消、加载状态和终端尺寸变化。 |
| UX-03 | P1 | 主题、快捷键、自定义布局及辅助使用；CLI 结构化输出便于脚本调用。 |
| PERF-01 | P0 | 按需加载、分页和有界缓存；无需启动浏览器引擎即可完成基本 TUI 阅读和 MCP 操作。 |
| PERF-02 | P0 | 建立可重复的空闲/读取/搜索/解析基准，记录 RSS/PSS、CPU、启动时间与输入延迟，包含 MCP 进程和必要子进程。 |
| PERF-03 | 待定 | 在架构原型阶段制定具体性能预算，明确邮件规模、硬件与冷热缓存条件；不用安装体积替代运行占用。 |

“精美”需通过实际界面评审确认；不以纯粹复刻成熟客户端作为设计要求。GUI 和跨平台能力后续评估。

## 9. 阶段计划与验收

### 阶段 A：架构与隐私原型

- 确定语言、库、解析器、OAuth/凭据方案与 TUI/MCP 共享核心设计，记录设计取舍和依赖许可证。
- 使用合成 MIME 邮件完成正文处理原型；覆盖外部样式、字体、媒体、嵌入页面、SVG、预取、内联/外部脚本、事件属性、控制序列和超大输入。
- 在受控测试环境验证解析、转换、TUI/MCP 输出及下游渲染均没有正文 HTTP/DNS 外联或脚本执行。不能仅靠字符串快照测试证明无网络请求。

### 阶段 B：真实邮件协议闭环

- 用受控 IMAP/SMTP 服务测试收取、搜索、草稿、回复、附件及发送；再经授权使用 Gmail OAuth 完成账户闭环。
- 验证 token 续期、撤销、证书错误、不修改已读状态的读取、断网与不确定发送结果恢复。
- 真实外发测试只向用户指定的测试账户进行，避免误发或批量操作。

### 阶段 C：TUI 与 Agent 工作流

- 人与 Agent 共用后端和隐私规则；验证权限限制、草稿可审阅、授权与内容绑定、MCP 输出安全和邮件指令不能自行触发操作。
- 实测中文、布局、键盘操作及性能预算；将验证方法和已知限制写入 docs。

### 阶段 D：开源发布准备

- 提供可运行的安装/测试说明、示例配置、许可证与依赖信息；检查仓库无真实邮件或秘密。
- 所有 P0 项有明确实现和验证结果后才称为首个可用于真实邮箱的版本。公开仓库及发行发布另按用户授权执行。

## 10. 待决策事项

- 语言与技术栈、是否复用现有邮件库、进程隔离方式及资源边界。
- 首版 TUI/CLI/MCP 命令和工具命名、发送审阅的具体交互、自动发送策略配置格式。
- OAuth client 的公共发行方式、凭据存储兼容方案、后续 Outlook 支持。
- 本地缓存格式、索引与加密、运行数据路径、跨设备同步语义。
- 性能预算、主题和视觉方向、GUI 与其他平台的时间安排。

上述事项不应被当前初始化文档视为已经选定；后续可在 `docs/` 中新增架构决策记录，并从本文件链接。
