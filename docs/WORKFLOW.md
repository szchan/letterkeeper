# Git、worktree 与 TDD 协作流程

2026-10-12 用户明确要求：Git 管理版本、worktree 隔离工作、主代理指导子代理、根据任务复杂度控制模型成本、开发记录写入 docs、TDD 与足量单元验证。

## 分工与模型

主代理负责需求、接口、集成、隐私/授权审查和最终验收。协议、解析、状态机优先使用 GPT-6.1-Sol high；界面/适配常规实现可用 GPT-6.1-Sol medium；文档、清单、已有代码的测试运行优先 GPT-6-Luna。遇到容量限制可用 GPT-6-Sol 接续。模型名称是本轮选择，不是对成本或可用性的永久承诺。复杂问题升级给主代理，不默认让所有任务使用最昂贵模型。

每个实现子任务给定独立分支、worktree、可改文件范围、公开 API 和验收测试。可以只读其他 worktree 以核对接口，但不跨 worktree 编辑。不要擅自覆盖用户改动；不明来源改动留在原处，集成时只挑选已审查提交。

## 开始与集成

1. 依次阅读 README、需求、LICENSE，再看当前 ADR 和 STATUS。
2. 确认 Git 状态，基于可构建基线创建 `.worktrees/任务名`；目录被忽略，私有运行数据只放 `.local/`。
3. 接口变化先通知其他任务。依赖版本由集成分支统一锁定；子代理不提交独立解析生成的 Cargo.lock。每个worktree保留独立target目录；不要共享会复用同名crate错误产物的编译目录。
4. 模块测试通过后提交，主代理审查并 cherry-pick；集成分支跑完整验证，再快进主分支。
5. 本地提交属于当前授权；推送、公开仓库、发行版与真实账户操作另按会话授权处理。

## TDD

- 先根据需求编号写行为/边界测试，再实现。尽可能用可编译 stub 让失败来自断言；API 尚不存在导致的编译 RED 也必须如实记录，不能伪装为行为失败。
- 运行并记录真实 RED 命令、失败原因，提交 `test:`；写最小实现直到 GREEN，提交 `feat:`/`fix:`；然后重构并维持测试通过。
- 新发现的 bug 必须先有能复现的回归测试。测试正向控制本身也要验证：网络监听器确实能接收父进程流量；测试子进程时保持 stdin 打开，避免 EOF 导致假通过。
- 每个逻辑单元覆盖正常、拒绝、边界、状态转换。跨进程持久化、并发争抢、断连以及不同下游适配用集成测试验证。测试可放在 crate 的 `tests/` 中，不以测试文件位置或单纯数量代替质量。
- 不盲目追求行覆盖率。只检查内部实现细节的测试不应取代安全性质、真实协议往返和终端行为测试。

## 完成条件

`cargo test --locked --workspace`、fmt、Clippy 无警告；涉及界面时运行真实 PTY 脚本；涉及正文时包含 sandbox HTTP/DNS/宿主文件检查；涉及发送时包含内容绑定、并发、重启及结果不确定测试。不得跳过失败项来让汇总通过。

每模块在 `docs/testing/` 写 RED/GREEN、验证环境和已知限制；设计取舍放 `docs/decisions/`，过程放 `docs/development/`。README 只列真实存在且验证过的入口，STATUS 区分原型通过与产品验收完成。
